# keycloak-reset-mail-spi

Two Keycloak SPIs backing the Equabli SSO migration:

1. **Reset-mail provider** (`com.equabli.keycloak.email`) — delegates the **Forgot Password** email
   to the Equabli **identity-service** instead of Keycloak's built-in SMTP sender.
2. **Migrated-user authenticator** (`com.equabli.keycloak.authenticator`) — a drop-in replacement
   for the browser flow's *Username Password Form* that emails bulk-migrated (passwordless) users a
   set-password + configure-TOTP link on their first sign-in attempt.

## Reset-mail provider

When a third party clicks "Forgot Password?" on the Keycloak login page, Keycloak's
reset-credentials flow generates its own action-token link and update-password page, then calls this
provider's `sendPasswordReset(link, expiration)`. The provider POSTs to identity-service, which
renders the branded `forgot-password` template and sends it via the notification service.

Only `sendPasswordReset` is overridden — every other Keycloak email keeps the default behaviour.

**Migrated (passwordless) users take the setup path instead.** If the user requesting "Forgot
Password?" has never set a password (a bulk-migrated user), there is nothing to *reset* — this is
really first-time account setup. In that case the provider sends the **"Set up your Equabli account"**
email instead: it builds an `UPDATE_PASSWORD` + `CONFIGURE_TOTP` action-token link and POSTs to the
**setup-password** endpoint (same branded mail as the [migrated-user authenticator](#migrated-user-authenticator)),
rather than the plain `UPDATE_PASSWORD` reset link and reset-password endpoint. Users who already have
a password get the normal reset email. The choice is automatic — no configuration.

## Migrated-user authenticator

Users bulk-migrated by the identity-service `POST /users/migrate` API exist in Keycloak with **no
password credential** and the `UPDATE_PASSWORD` + `CONFIGURE_TOTP` required actions. They can never
pass the standard password form, so `MigratedUserAuthenticator` (extends the built-in
`UsernamePasswordForm`) intercepts the form submit: if the submitted username resolves to an
enabled user without a password credential, it

1. builds an `ExecuteActionsActionToken` link (UPDATE_PASSWORD + CONFIGURE_TOTP, expiring after the
   realm's *Action token generated by admin* lifespan),
2. POSTs `{email, firstName, link}` to identity-service's
   `/public/user/internal/setup-password-email`, which sends the branded `setup-password` email, and
3. shows Keycloak's standard "You should receive an email shortly" info page.

For every other user it behaves exactly like the built-in form. A per-user cooldown (user attribute
`setupMailSentAt`, default 900s, override via `IDENTITY_SERVICE_SETUP_MAIL_COOLDOWN_SECONDS`)
prevents repeated login attempts from firing an email each time.

### Post-setup redirect (where the user lands afterwards)

Once a user finishes setting the password (and enrolling TOTP) — from a migrated-user login or from
"Forgot Password?" — they should land back on the site they started from (e.g. a user who opened
`stage.tenant.equabli.io` returns to `stage.tenant.equabli.io`), whatever their org type. Every
tenant URL is different, and Keycloak's *Valid Redirect URIs* only allow a trailing `*` on the
**path**, never in the host, so the per-tenant URLs can't be registered individually. Instead the
`reduri` in the action token always points at **one stable identity-service forwarder endpoint**
carrying the Keycloak user id and the Keycloak client the user came from:

```
https://dev.equabli.io/identity-service/api/public/user/post-setup-redirect?uid=<keycloakUserId>&cid=<keycloakClientId>
```

That endpoint (`UserPublicController#postSetupRedirect`) owns **all** destination logic: it
302-redirects to the `cid` client's **Home URL**; without a usable one it falls back to the user's
client/partner `env_instance_url` from the database, then `user-activation-baselink`. The SPI only
reports where the user came from — it never picks the destination. `cid` is omitted when there is no
authentication session (admin-triggered emails), so those users go to their instance URL. The
forwarder URL is built from the **base URL** (`IDENTITY_SERVICE_BASE_URL`, dev default baked into the
jar) plus the fixed forwarder path — the SPI appends the path, `?uid=…` and `&cid=…` itself via
`IdentityServiceConstants.postSetupRedirectUrl(realm, userId, clientId)` (see
[Configure](#configure-environment-variables-on-the-keycloak-process)).

> **The `*` wildcard belongs only in the Keycloak client's *Valid Redirect URIs*, never in
> `IDENTITY_SERVICE_BASE_URL`.** The forwarder is the *real URL the browser is redirected to* — a
> literal `*` in it makes a non-routable URL and the redirect fails. The client's *Valid Redirect
> URIs* entry is a matching pattern, not a target, so it takes the trailing `*`. Concretely:
>
> | Place | Value | Has `*`? |
> |---|---|---|
> | Env var `IDENTITY_SERVICE_BASE_URL` | `https://dev.equabli.io` | **No** |
> | Resolved forwarder URL (built by the SPI) | `https://dev.equabli.io/identity-service/api/public/user/post-setup-redirect` | **No** |
> | Client → Valid Redirect URIs | `https://dev.equabli.io/identity-service/api/public/user/post-setup-redirect*` | **Yes** |

**Client config (required for the redirect):** the token's `azp` client (the app the user was signing
into) must list the forwarder URL — *with* the trailing `*` — under **Clients → *client* → Valid
redirect URIs**. Without it, the action-token page fails with `400 Bad Request` (invalid redirect uri).

**Flow binding (required — the authenticator is not picked up automatically):** in the admin
console, duplicate the realm's **browser** flow, replace the *Username Password Form* execution
inside the forms subflow with **Username Password Form (Migration Setup Email)** (same requirement),
and bind the copy as the realm's Browser Flow.

**Home URL per front-end (required for "return to where you came from"):** the site a user started
from can't be derived from the login request when the client is a Cloudflare Access IdP integration
— Cloudflare's callback URL is the same for every app behind it, so Keycloak never sees the real
front-end host. Instead, give each front-end its own Keycloak client (its own Cloudflare Access
identity-provider integration — see
[NEW_REALM_CHECKLIST.md](NEW_REALM_CHECKLIST.md#1-cloudflare-access-oidc-client)) and set that
client's **Home URL** (Settings tab) to its real origin, e.g. `https://stage.tenant.equabli.io`. The
forwarder reads it through the Keycloak admin API, so identity-service's `identity-service` admin
client needs the `realm-management` **`view-clients`** role. Only the forwarder URL needs to be in
the client's Valid Redirect URIs — the Home URL does not, because Keycloak redirects to the forwarder
and identity-service issues the final 302.

> **New-realm gotcha:** when duplicating the browser flow for a new realm, check the config (gear
> icon) on the **User session count limiter** execution that precedes the password form. If it was
> copied with a stale/leftover session-limit config (or one meant for a different realm), it can
> reject every login *before* the password form ever renders — with a generic
> `AuthenticationFlowException` in the server log and no useful client-facing error, which looks like
> a flow-binding or SPI problem but isn't. Leave it unconfigured (as in the working reference realm)
> unless you actually want a session cap.

## Build

```
mvn -f keycloak-reset-mail-spi/pom.xml clean package
# => target/keycloak-reset-mail-spi.jar
```

Set `<keycloak.version>` in `pom.xml` to your exact server version if it isn't 26.0.9.

## Deploy

Copy the jar into the Keycloak `providers/` directory and rebuild the server:

```
cp target/keycloak-reset-mail-spi.jar /opt/keycloak/providers/
/opt/keycloak/bin/kc.sh build
```

(For the Keycloak container image, `COPY` the jar into `/opt/keycloak/providers/` before
`kc.sh build` in your Dockerfile.)

## Configure (environment variables on the Keycloak process)

**Only the base URL changes between environments/tenants.** It supplies the scheme + host only; the
SPI appends the fixed endpoint paths itself (reset-mail, setup-mail, and the post-setup forwarder).
All defaults live in one place — `com.equabli.keycloak.IdentityServiceConstants`.

It resolves in this order (see `IdentityServiceConstants.baseUrl(RealmModel)`):

1. **Realm attribute** `identityServiceBaseUrl` — the admin console has **no UI for generic realm
   attributes** (unlike the per-client/per-user Attributes tabs), so this must be set via `kcadm` or
   the Admin REST API:
   ```
   kcadm.sh update realms/<realm> -s 'attributes.identityServiceBaseUrl=https://tenant.equabli.io'
   ```
   Use this when **one Keycloak server hosts multiple realms that each need a different
   identity-service** — no server restart required, and it can be changed at any time.
2. **`IDENTITY_SERVICE_BASE_URL`** env var on the Keycloak process — a server-wide default for
   realms that don't set the attribute above.
3. **Dev default** baked into the jar (`https://dev.equabli.io`).

| Variable / attribute | Example | Required |
|---|---|---|
| Realm attribute `identityServiceBaseUrl` | `https://dev.equabli.io` (scheme + host **only** — no path, no trailing `/`, no `*`) | No — only needed when a realm must override the env-var/default |
| `IDENTITY_SERVICE_BASE_URL` | `https://dev.equabli.io` (scheme + host **only** — no path, no trailing `/`, no `*`) | No (dev default baked in) |
| `IDENTITY_SERVICE_RESET_MAIL_SECRET` | a strong random string (shared by both mail callbacks) | Yes in real envs |
| `IDENTITY_SERVICE_SETUP_MAIL_COOLDOWN_SECONDS` | `900` (optional) | No |

The base URL resolves to these full endpoints (paths are fixed in `IdentityServiceConstants`):

| Purpose | Resolved URL |
|---|---|
| Reset-password mail callback | `<base>/identity-service/api/public/user/internal/reset-password-email` |
| Setup-password mail callback | `<base>/identity-service/api/public/user/internal/setup-password-email` |
| Post-setup redirect forwarder | `<base>/identity-service/api/public/user/post-setup-redirect` |

The secret must equal the identity-service property `internal.reset-mail-secret`
(env `INTERNAL_RESET_MAIL_SECRET`). The base URL and secret fall back to dev defaults baked into the
jar — always override them in every real environment.

> **Migrating from an older build?** The previous per-endpoint full-URL variables
> (`IDENTITY_SERVICE_RESET_MAIL_URL`, `IDENTITY_SERVICE_SETUP_MAIL_URL`,
> `IDENTITY_SERVICE_POST_SETUP_REDIRECT_URL`) are **no longer read** — replace all three with the
> single `IDENTITY_SERVICE_BASE_URL`.

## Verify

Forgot-password path:

1. On the Keycloak login page click **Forgot Password?**, enter a known user's email.
2. identity-service logs `Keycloak password reset mail queued for <email>`.
3. The email arrives via the notification service; its link points back to Keycloak's
   update-password page. Setting a new password there completes the reset.

Migrated-user path:

1. Run identity-service `POST /users/migrate?dryRun=false`, then attempt to sign in at Keycloak as
   a migrated user (any password).
2. The login page shows "You should receive an email shortly…"; identity-service logs
   `Password setup mail queued for <email>`.
3. The emailed link opens Keycloak's set-password page, then TOTP enrollment; afterwards the user
   is returned to the application and can sign in normally.
